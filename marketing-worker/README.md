# Marketing reminders

This Worker has no cron and sending is disabled by default. Deploy the Pages backend first so registration creates the table and records prospective activity. The standalone Node commercial server does not implement marketing consent, activity tracking, or unsubscribe and must not be used for signups for this campaign.

Frontend integration: send `marketingOptIn: true` only when a registrant explicitly checks an optional marketing consent checkbox; omitted or false means no consent. The field is ignored for existing users signing in. Existing accounts are not enrolled. Provide clear consent language covering marketing emails; transactional verification emails remain separate.

To enable, configure the same strong random `MARKETING_UNSUBSCRIBE_SECRET` as a secret on Pages and this Worker, plus Worker secrets `RESEND_API_KEY` and `MARKETING_FROM_EMAIL` (a verified sender). Set Worker variables `MARKETING_SENDER_NAME` to the business name, `MARKETING_POSTAL_ADDRESS` to its valid physical postal address, and `APP_ORIGIN` to the HTTPS public site origin and `MARKETING_REMINDERS_ENABLED` to `true`; set `GENERATION_ENABLED=false` on the Worker to suppress sends during an outage. This variable is independent of the Pages setting, so changing Pages alone does not pause the Worker. Add a daily `[triggers]` section with `crons = ["0 10 * * *"]` to this Worker's wrangler.toml and deploy it separately with `npx wrangler deploy --config marketing-worker/wrangler.toml`. Do not enable until signup consent UI is live and tested. Rotating the unsubscribe secret invalidates existing links; retain the secret for as long as links must work.

The Worker sends at most one reminder per signup, seven days after signup or the last accepted generation attempt, whichever is later. It checks verified active accounts, consent, remaining credits, current configured generation costs, and active generation leases. Attempts that pass the generation safety reservation count as activity even if the later generation fails; requests rejected before that reservation do not count. Attempts predating deployment are unknown; only signups with a prospective baseline are eligible. Opt-outs use a signed opaque link, GET confirmation, and POST; one-click unsubscribe is supported. The Worker claims before sending. A 429 rate-limit response releases the claim for a later retry. Authentication failures (401 and 403) also release the claim and stop the batch so configuration can be fixed. Other rejections and ambiguous outcomes remain claimed. Provider errors are logged without recipient details. Up to 50 eligible records are examined per invocation. Monitor logs and adjust capacity if volume grows. Persistent 429 responses can delay later recipients until the provider accepts requests. Database checks and external mail delivery cannot be atomic: a last-moment opt-out or generation can race the provider request, and the balance can change after the final read.

If recording generation activity fails, the API attempts to suppress that user’s marketing and continues generation. If the suppression write also fails, generation stops before charging because inactivity cannot otherwise be tracked safely.
